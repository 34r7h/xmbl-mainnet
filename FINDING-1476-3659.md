# Why the landmark reads 1476/3659 and cannot advance

Measured 2026-09-24T17:2xZ against the live broker. Reproduced the badge arithmetic exactly
(1485/3659 at read time; 1476 in the screenshot — `faces_sealed` had ticked 164 -> 165).

## The badge

`web/static/network3d.js:1230` — `XMBL · ${finalN}/${txCount}`

- `txCount` = `anchors_on_chain` = **3659** — the broker's full ordered anchor ledger.
- `finalN`  = `min(txCount, sealedBlocksOf(ch))` = **1476** = `faces_sealed × 9` = 164 × 9.

`sealedBlocksOf` returns `max(mp.final, selfFaces, rootHeight, ...peerApplied, ...peerFaces)`:

| candidate | value | note |
|---|---|---|
| `mempool.final` | 0 | drain queue, empty |
| `selfFaces` / `peerFaces` = `faces_sealed × 9` | **1485** | **selected — it is the max** |
| `rootHeight` | 0 | suppressed, see below |
| `peerApplied` = `applied_tx_count` | 828 | the only candidate in the denominator's unit |

## Three compounding reasons it is stuck

1. **Unit mismatch.** The numerator that wins the `max()` is `faces_sealed × 9` — seal rounds since
   boot — while the denominator counts anchors in the broker's ledger. `max()` picks faces×9
   *because* it is the larger number, so the displayed progress is the one candidate that is not in
   the denominator's unit. `applied_tx_count` (828) is in the right unit and is discarded for being
   smaller.

2. **The honest numerator is suppressed by construction.** `eligible_roots[0]` = height 1485 backed
   by `nodes: 1`. `unanimous` requires `er[0].nodes >= Math.max(2, nodes_reporting)`. Exactly one
   coordinator hosts a node network-wide, so `1 >= 2` is false and `rootHeight` is thrown away on
   every read. The ≥2 floor makes the state-height signal unusable on a single-node network forever.

3. **The node can only ever receive 826 of the 3659 anchors, and that is correct.** 2,831 of them
   predate the typing epoch (`first_typed_ts` 2026-09-16T07:52:35.155Z) and carry no xid. This
   node's ledger refuses untyped rows (`ledger_capabilities.requires_typed_anchors`), so the
   coordinator correctly fetches `?from_epoch=1` — which returns exactly **826**. The node's
   `applied_tx_count` is **828**: it has applied every anchor it is entitled to. Against the right
   denominator this node is complete, not stuck.

## Nothing in packages/core moves this number

Both candidate protocol changes were checked and neither works:

- Flipping `requires_typed_anchors` to false: measured the ledger's dry pass over the live 3659-row
  default feed — `would_rebuild = 828, untyped = 2831, rejected = 0`, so the would-empty-the-chain
  guard does NOT fire and the feed is safe. But it only adds verkle keys and 2 anchor blocks. It
  does not touch `faces_sealed`, so the badge does not move.
- `apply_canonical` never seals faces, so feeding the node the full set cannot raise the numerator
  either.

Every lever is on the handoff side: `sealedBlocksOf`, the `unanimous` ≥2-node gate and
`txCount = anchors_on_chain`, all in `web/static/network3d.js`, plus the `anchors_on_chain` field in
the broker payload.

## The fix that would work

Prefer `applied_tx_count` over `faces_sealed × 9` when the node reports it (it is bounded by the
ledger and in the same unit), or drop the `Math.max(2, …)` floor so a single-node network can use
`eligible_roots[].height`. Either makes the ratio honest; the first also makes it reachable.
